Kubernetes监控管理工具prometheus-operator

發表於 2019-12-03

OOO-Operator by CoreOSs

在以往原生的 Kubernetes 環境裡，管理維護 stateful service 是件困難的工作。雖然 kubernetes 有提供 statefulSet 這樣的物件，但對於要維護 stateful service 來說還是相當不足的。舉例來說，當建立一個 mysql 的 stateful service 時，我們可能希望第一個 pod 是 master，第二個 pod 對 master 做 replication，第三個 pod 對第二個 pod 做 replication。這樣的架構如果要靠 kubernets 管理者來設定的話，會需要對 mysql 有一定的了解才能進行，而且可能相當耗費心力。
而每種 stateful service 的管理維護方式都各有巧妙不同，像 redis、kafka、prometheus 等，這些都需要嫻熟於該領域的人，才知道最好的管理方式為何。因此 stateful service 一直是讓 Kubernetes 使用者相當困擾的事情，比較安全的做法往往都是放棄讓 stateful service 跑在 kubernetes 裡，用傳統的方式來維運，一直到 operator 的出現。

對於在 Kubernetes 上維運 stateful service 的困難，CoreOS 這家公司看出了需求與契機，開發了 Operator 這種專門處理 stateful service 的機制。透過擴展 Kubernetes 的 API 與相對應的 controller，可以用更好更安全的方式來建立、配置和管理 stateful service。於是短短一兩年時間，許多軟體廠商開始主動提供 operator 的套件來協助使用者將其軟體放到 Kubernetes 維運，也因此 operator 也成為 Kubernetes 領域裡的顯學之一。

Operator 的架構主要可以分成兩部分，一個是 CRD (使用者自定義資源，CustomResourceDefinition)，另一個是 controllers，而 controller 就是處理當 CRD 發生 CRUD 操作時的相對應動作。例如 CRD 可能是定義一個叫 mysqldatabase 的資源物件，當kuberetes API 收到有 mysqldatabase 要建立時，會透過相對應的 controller 來建立相關的資源物件。
是知名且良好的 operator 套件，多半是原廠或該領域的專家所提供，通常都提供了許多便利且安全的機制，讓使用者可以用簡單且符合 Kubernetes 架構的方式來管理使用，而 Prometheus-Operator 也是其中之一

Kubernetes管理集群服务的外部访问Ingress

發表於 2019-11-29

一个 API 对象，用于管理对集群中服务的外部访问，通常是 HTTP。Ingress 可以提供负载平衡，SSL 终端和基于名称的虚拟主机。

Ingress是什麼？

Ingress公开了从群集外部到群集内 services 的HTTP和HTTPS路由。 流量路由由Ingress资源上定义的规则控制。

可以将Ingress配置为提供服务外部可访问的URL，负载平衡流量，终止 SSL / TLS 并提供基于名称的虚拟主机。 Ingress 控制器通常负责通过负载平衡器来实现入口，尽管它也可以配置边缘路由器或其他前端以帮助处理流量。

Ingress 不会公开任意端口或协议。 将 HTTP 和 HTTPS 以外的服务公开给 Internet 时，通常使用以下类型的服务 Service.Type=NodePort 或者 Service.Type=LoadBalancer.

Ingress控制器

您必须具有 Ingress 控制器才能满足Ingress的要求。 仅创建Ingress资源无效。

GCE／Google Kubernetes Engine 是在主节点上部署 Ingress 控制器。 您可以在 Pod 中部署任意数量的自定义 Ingress 控制器。 一定要检查一下这个控制器的 beta 限制。 在 GCE／Google Kubernetes Engine 之外的环境中，需要将控制器部署 为 Pod。

RBAC

Kubernetes在1.6+中引入了基於角色的訪問控制（RBAC），以實現對Kubernetes資源和API的細粒度控制。
如果您的集群配置了RBAC，則需要授權Traefik使用Kubernetes API。有兩種設置適當權限的方法：通過特定於名稱空間的RoleBindings或單個全局ClusterRoleBinding。
每個命名空間的RoleBindings可以將授予的權限僅限制於Traefik所監視的命名空間，從而遵循最小特權原則。如果不應讓Traefik監視所有名稱空間，並且名稱空間集不會動態更改，則這是首選方法。否則，必須使用單個ClusterRoleBinding。

Kubernetes儲存StorageClass

發表於 2019-11-28

Volume介绍

與管理計算實例相比，管理存儲是一個明顯的問題。該PersistentVolume子系統提供了用戶和管理員抽象的存儲如何從它是如何消費提供信息的API。為此，我們引入了兩個新的API資源：PersistentVolume(PV)和PersistentVolumeClaim(PVC)。
PV是集群中的資源。PVC是對這些資源的請求，並且還充當對資源的聲明檢查。可以通過兩種方式設置PV：靜態或動態。

  1. 靜態
    集群管理員創建許多PV。它們帶有實際存儲的詳細信息，可供群集用戶使用。它們存在於Kubernetes API中，可供使用。 (使用上不方便)

  2. 動態 (推薦)
    此供應基於StorageClasses：PVC必須請求 存儲類，並且管理員必須已經創建並配置了該類，才能進行動態供應。要求該類的聲明””實際上為其自身禁用了動態預配置。要基於存儲類別啟用動態存儲配置，集群管理員需要 在API服務器上啟用DefaultStorageClass。

PersistentVolume介绍

PersistentVolume可以當成是 Kubernetes Cluster 中專們用來儲存資料的地方。不但能將 container 的資料儲存下來，也可以透過掛載(mounting)的方式，供許多個 Pods 同時存取。
