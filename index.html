EFK介紹說明

Elasticsearch ：一套分散式的 Log 訊息搜尋引擎。基於 Apache Lucene(TM) 所開發的搜尋引擎，可以透過全文搜尋、結構化搜尋和分析這三種功能組合再一起搜尋 Log 訊息，此外 Elasticsearch 具有高擴展性、高可用性、易管理等特點。知名的 Wikipedia 、 Stack Overflow 、 GitHub等搜尋引擎底層都採用這一套系統，由此可見 Elasticsearch 的強大與實用。

Fluentd ： 是一個 Log 訊息收集的工具。支援各種不同的資料來源如：Application Logs 、 Network Protocols 、 IOT Devices Logs 等等，並有豐富的 Plugins 可以對資料進行過濾、分析、統一格式一系列的操作，最後可以將資料輸出到各式各樣的後端儲存平台上如 AWS S3 、 MySQL 、 Hadoop DFS 等儲存平台。

Kibana ：提供一個資料視覺化的操作平台。使用者能夠透過 Kibana 快速的將 Elasticsearch 中所查詢到的資料生成圖表、表格、地圖以較為圖像式的方式呈現。

由上述三個開源專案我們可以清楚的看到他們強大的特性與功能，這邊做一個簡單的整理與分類。

  • Log 訊息的分析、搜尋 Elasticsearch
  • Log 訊息的發送接收、儲存與資料格式統一 Fluentd
  • Log 訊息轉為圖表、表格、地圖等視覺化資料 Kibana

訊息佇列服務-RabbitMQ on Kubernetes

RabbitMQ介紹說明

RabbitMQ is an open source message broker software that implements the Advanced Message Queuing Protocol (AMQP).

RabbitMQ文檔說明

高併發下RabbitMQ限流實踐

業務場景

舉一些我們平常生活中的消費場景，例如：火車票、機票等，通常來說這些服務在下單之後，後續的出票結果都是異步通知的，如果服務本身只支持每秒1000訪問量，由於外部服務的原因突然訪問量增加到每秒2000並發，這個時候服務接收者因為流量的劇增，超過了自己系統本身所能處理的最大峰值，如果沒有對消息做限流措施，系統在這段時間內就會造成不可用，在生產環境這是一個很严重的問題，實際應用場景不止於這些，本文通過RabbitMQ來講解如何對消費端做限流措施。

消費端限流機制

RabbitMQ提供了服務質量保證( QOS)功能，對channel（通道）預先設置一定的消息數目，每次發送的消息條數都是基於預先設置的數目，如果消費端一旦有未確認的消息，這時服務端將不會再發送新的消費消息，直到消費端將消息進行完全確認，注意：此時消費端不能設置自動簽收，否則會無效。

在之後，放寬了限制，除了對channel設置之外，還可以對每個消費者進行設置。

Kubernetes监控管理工具prometheus-operator

發表於 2020-02-01

OOO-Operator by CoreOSs

在以往原生的 Kubernetes 環境裡，管理維護 stateful service 是件困難的工作。雖然 kubernetes 有提供 statefulSet 這樣的物件，但對於要維護 stateful service 來說還是相當不足的。舉例來說，當建立一個 mysql 的 stateful service 時，我們可能希望第一個 pod 是 master，第二個 pod 對 master 做 replication，第三個 pod 對第二個 pod 做 replication。這樣的架構如果要靠 kubernets 管理者來設定的話，會需要對 mysql 有一定的了解才能進行，而且可能相當耗費心力。
而每種 stateful service 的管理維護方式都各有巧妙不同，像 redis、kafka、prometheus 等，這些都需要嫻熟於該領域的人，才知道最好的管理方式為何。因此 stateful service 一直是讓 Kubernetes 使用者相當困擾的事情，比較安全的做法往往都是放棄讓 stateful service 跑在 kubernetes 裡，用傳統的方式來維運，一直到 operator 的出現。

對於在 Kubernetes 上維運 stateful service 的困難，CoreOS 這家公司看出了需求與契機，開發了 Operator 這種專門處理 stateful service 的機制。透過擴展 Kubernetes 的 API 與相對應的 controller，可以用更好更安全的方式來建立、配置和管理 stateful service。於是短短一兩年時間，許多軟體廠商開始主動提供 operator 的套件來協助使用者將其軟體放到 Kubernetes 維運，也因此 operator 也成為 Kubernetes 領域裡的顯學之一。

Operator 的架構主要可以分成兩部分，一個是 CRD (使用者自定義資源，CustomResourceDefinition)，另一個是 controllers，而 controller 就是處理當 CRD 發生 CRUD 操作時的相對應動作。例如 CRD 可能是定義一個叫 mysqldatabase 的資源物件，當kuberetes API 收到有 mysqldatabase 要建立時，會透過相對應的 controller 來建立相關的資源物件。
是知名且良好的 operator 套件，多半是原廠或該領域的專家所提供，通常都提供了許多便利且安全的機制，讓使用者可以用簡單且符合 Kubernetes 架構的方式來管理使用，而 Prometheus-Operator 也是其中之一

Kubernetes HA環境概述

由於資源限制，原本應該獨立的HA Proxy主機，因資源夠大，所以合併作為Worker01用了。
